## 1. Общее состояние проекта

### ✅ Что уже реализовано:
- Базовая аутентификация через Telegram Mini Apps

## 2. Критические проблемы

### 🔴 КРИТ-1: Утечка JWT секрета в .env файле

**Файл:** `.env`

**Проблема:**
```dotenv
JWT_SECRET=your_super_secret_jwt_key_min_32_characters_long
```
JWT секрет - стандартный placeholder из примера! Это критическая уязвимость.

**Влияние:** Любой может подделать JWT токены

**Решение:** Сгенерировать уникальный 64+ символьный секрет:
```bash
node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
```

---

### 🔴 КРИТ-2: Telegram Bot Token в репозитории

**Файл:** `.env`

**Проблема:** Реальный bot token виден в файле .env (который не должен быть в репозитории)
```
TELEGRAM_BOT_TOKEN=8316828513:AAFcEZbSf-5EL5zpRFwYEwK7aZCaOyEIV9I
```

**Влияние:** Токен скомпрометирован, бот может быть взломан

**Решение:**
1. Немедленно отозвать токен через @BotFather (`/revoke`)
2. Получить новый токен
3. Добавить `.env` в `.gitignore`
4. Удалить `.env` из истории git (`git filter-branch` или `bfg`)

---

### 🔴 КРИТ-3: DATABASE_URL с credentials в репозитории

**Файл:** `.env`

**Проблема:** Реальные данные подключения к Neon DB видны
```
DATABASE_URL=postgresql://neondb_owner:npg_my8lc7NgiaQG@ep-delicate-boat-adl99rqg-pooler...
```

**Влияние:** Полный доступ к БД для злоумышленников

**Решение:**
1. Сменить пароль в Neon dashboard
2. Использовать секреты окружения, не хранить в репозитории

---

### 🔴 КРИТ-4: Отсутствие .gitignore для .env

**Проблема:** Файл `.env` с секретами находится (или находился) в репозитории

**Решение:** Проверить/создать `.gitignore`:
```gitignore
.env
.env.local
.env.*.local
```

## 3. Архитектурные проблемы

### 🟠 АРХ-1: Смешение ответственности в storage.ts

**Файл:** `server/storage.ts`

**Проблема:** Класс `DatabaseStorage` напрямую работает с пользователями, сообщениями и комнатами. При росте проекта это приведёт к God Object.

**Задача:** Разделить на отдельные репозитории:
- `UserRepository`
- `MessageRepository`  
- `RoomRepository`

---

### 🟠 АРХ-2: Отсутствует слой сервисов

**Проблема:** Бизнес-логика размазана между `routes.ts`, `websocket.ts` и `storage.ts`.

**Пример:** Логика обновления профиля в `routes.ts`:
- Валидация (Zod)
- Санитизация
- Сохранение
- Отметка о завершении

**Задача:** Создать слой сервисов:
```
server/services/
  ├── UserService.ts
  ├── MessageService.ts
  ├── ProfileService.ts
  └── AuthService.ts
```

---

### 🟠 АРХ-3: Дублирование типов User/Message

**Проблема:** Интерфейсы User, Message определены в нескольких местах:
- `shared/schema.ts` (основные типы)
- `client/src/pages/chat.tsx` (локальные интерфейсы)
- `client/src/components/chat-interface.tsx` (локальные интерфейсы)

**Задача:** Использовать единые типы из `shared/schema.ts` везде

---

### 🟠 АРХ-4: Несогласованность порта сервера

**Проблема:** В разных файлах указаны разные порты:
- `.env`: `PORT=3000`
- `.env.example`: `PORT=5000`
- В коде есть упоминания обоих

**Задача:** Унифицировать до одного порта (рекомендуется 3000)

## 5. Проблемы безопасности

### ✅ SEC-1: Dev endpoint защищён — ИСПРАВЛЕНО

**Файл:** `server/routes.ts`

**Решение:** Dev endpoint `/api/auth/dev` теперь имеет 4 уровня защиты:
1. Проверка `NODE_ENV !== 'production'`
2. Проверка `DEV_MODE === 'true'`
3. Проверка длины JWT_SECRET (production секрет блокируется)
4. IP whitelist (только localhost)

---

### 🟠 SEC-2: Отсутствие CORS настройки

**Файл:** `server/index.ts`

**Проблема:** CORS не настроен - любой домен может отправлять запросы

**Задача:** Добавить cors middleware:
```typescript
import cors from 'cors';
app.use(cors({
  origin: process.env.WEBAPP_URL,
  credentials: true
}));
```

---

### 🟠 SEC-3: Слабая валидация initData

**Файл:** `server/routes.ts`, функция `verifyInitData`

**Проблема:** Нет проверки `auth_date` - старые initData принимаются как валидные

**Задача:** Добавить проверку времени:
```typescript
const authDate = parseInt(kv['auth_date'] || '0');
const now = Math.floor(Date.now() / 1000);
if (now - authDate > 86400) { // 24 часа
  return false; // initData устарел
}
```

---

### 🟠 SEC-4: Нет ограничения размера сообщений

**Файл:** `server/websocket.ts`

**Проблема:** Только валидация Zod, нет явного лимита длины сообщения на WebSocket уровне

**Задача:** Добавить проверку:
```typescript
if (content.length > 4000) {
  ws.send(JSON.stringify({ type: 'error', message: 'Message too long' }));
  return;
}
```

---

### ✅ SEC-5: Проверка загружаемых файлов — ИСПРАВЛЕНО

**Файл:** `server/routes.ts`

**Решение:** Добавлена проверка magic bytes с помощью библиотеки `file-type`:
- Функция `validateImageMagicBytes()` проверяет реальный тип файла
- Невалидные файлы автоматически удаляются
- Поддержка JPEG, PNG, GIF, WebP

## 8. Проблемы производительности

### 🟠 PERF-1: Отсутствие кэширования

**Проблема:** Нет Redis или аналогичного кэша для:
- Профилей пользователей (частые запросы)
- Количества онлайн пользователей (вычисляется на каждый broadcast)
- Топ пользователей (пересчитывается на каждый запрос)

**Задача:** Внедрить Redis для кэширования

---

### 🟠 PERF-2: N+1 проблема в getMessagesByRoomId

**Файл:** `server/storage.ts`

**Проблема:** Используется `leftJoin`, но для 50 сообщений может создавать overhead

**Задача:** Профилировать запросы, при необходимости оптимизировать

---

### 🟡 PERF-3: Broadcast всем клиентам

**Файл:** `server/websocket.ts`

**Проблема:** `broadcastOnlineCount` рассылает сообщение ВСЕМ подключённым клиентам при каждом connect/disconnect

**Задача:** Debounce уже есть (1 сек), но при большом количестве пользователей нужно рассмотреть pub/sub через Redis

---

### 🟡 PERF-4: Нет индексов на новых таблицах

**Файлы:**
- `shared/schema.ts` - таблицы `profileViews`, `friendRequests`, `news`
- `migrations/001_add_indexes.sql` - только базовые таблицы

**Задача:** Создать миграцию с индексами для статистических таблиц:
```sql
CREATE INDEX idx_profile_views_profile ON profile_views(profile_user_id);
CREATE INDEX idx_friend_requests_to ON friend_requests(to_user_id);
CREATE INDEX idx_news_created ON news(created_at DESC);
```
